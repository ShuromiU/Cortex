# Cortex

A trust, freshness, and economy layer for coding-agent memory, not a transcript store. A remembered item carries whether it is still agreed (`[contested]`, `(superseded)`), whether it still describes the checkout (`[stale:`, `[moved:`), and what it cost (every retrieval channel budgeted; `cortex stats` reports injected/saved/net, and the credit side is now **evidence-only** — the consolidation estimate that produced it is withdrawn, so `Saved` reads 0 until verified substitution ships). `README.md` carries the positioning and the honest comparison against platform auto-memory; this file is the invariants log.

## Current Model
- Cortex is retrieval-first, not transcript-first, and pull-based, not push-based: a tiny validated session brief at startup plus the high-confidence reflex are the memory channels; coercion is reduced to one one-line hint per session.
- Sessions are branch/worktree-aware.
- `memory_items` is the canonical search/retrieval layer.
- Default state starts with current-session load-bearing notes, then uses the scored working set, within a token budget.
- Cortex tracks a lightweight current app graph, validates file/path references extracted from memory, and resolves renamed files through a git rename map (`[moved:]`) instead of treating them as missing.
- Memory decays through `hot`, `warm`, `cold`; recalled/touched memory is reinforced; `archived` is a preserved legacy tier (pre-1.4 supersedes) that no current path produces, still honored by every query filter and collected by GC. `cortex gc` bounds growth of derived data (dry-run by default).
- Ambient capture is spooled (`.cortex.spool.jsonl`, bash append, batch flush at turn end / 256 KiB / next session start) instead of spawning Node per tool call; engagement state lives in `<project>/.cortex.state`.
- Note-backed recall, brief, state, and reflex output includes compact UTC timestamps; recall/brief are answer-shaped and budgeted.
- Retrieval quality is benchmarked with hermetic seeded fixture suites in `eval/suites/` (reference results in `eval/baselines/`); optional semantic retrieval is gated by `CORTEX_SEMANTIC_MODE=off|shadow|rank`.

## Expected Behavior
- `inject-header --quiet` is wired to SessionStart. It flushes leftover spool lines into the session they belong to, creates a scoped session, flips `<project>/.cortex.state` to `enabled=true`, and prints the validated session brief (≤150 tokens) — or nothing on a cold start.
- `cortex reflect` is hook-facing and emits short `additionalContext` only for high-confidence remembered focus shifts; silence is the default.
- `cortex_route` / `cortex route` are the cold-callable capability map.
- Deferred tool discovery should use callable-name discovery (`ToolSearch`/`tool_search` query `cortex_recall`, `cortex_state`, or `cortex_route`) or server-name bootstrap (`Cortex`). Canonical `select:mcp__cortex__...` selectors may return 0 on current Codex app-server builds and are not proof Cortex is unavailable.
- `cortex_state` should show current-session load-bearing notes first, then the current working set, within its budget (default 800 tokens), never an empty `Branch snapshot:` header or duplicated evidence lines.
- Empty `cortex_state` should return actionable fallback guidance, not an empty string.
- `cortex_recall` and `cortex_brief` should search notes, snapshots, summaries, and command/episode memory, lead with a most-relevant line plus trust label, and respect their budgets.
- Retrieval should rank current-valid memories above memories pointing at missing files; stale memories stay reachable in top results with a `[stale: missing ...]` label (graduated capped penalty, never buried); renamed files resolve to `[moved: a → b]` via the rename map or unique-basename fallback.
- The rerank layer counts stemmed token hits (`testing` matches `test flake`); the FTS layer already stems via its porter tokenizer.
- Note renderers should preserve `Kind [YYYY-MM-DD HH:mmZ]: ...` timestamp format for agent-readable chronology.
- Retrieval should expose score breakdowns (`detail: 'scores'`) for quality evaluation and respect temporal terms such as latest/current, old/history, resolved, and when.
- Semantic ranking must remain optional; `off` is default, `shadow` must not change returned results, and `rank` must be tested with deterministic fake providers.
- Sessions are identified by `(scope_key, agent_id)`. A hook payload carrying `agent_id` resolves to a child session created on demand under the active primary — recording `parent_session_id` and `agent_type`, inheriting the primary's scope — and a payload without one resolves to the primary. A subagent payload never rotates or ends the primary it belongs to, whatever its own `cwd` resolves to. `reflect-*` and `end-of-turn` resolve to the primary by design.
- The PostToolUse hook writes `agent_id`/`agent_type` onto each spool line, omitting both when absent, and the flush resolves every entry to its own session — so subagent tool calls reach their own child session on the installed Claude path, not just through direct `hook-entry post` calls. Lines written by a hook installed before agent identity carry no such fields and still resolve to the primary; re-run `cortex install-hooks --claude` to update a stale script.
- The `command_failure` fold is scoped to the recording session: a repeated identical failure within one session bumps its occurrence count, but two sessions that each hit the same failure each keep their own episode. Unscoped, whichever session failed first owned the episode — so a subagent failing before its parent left the parent with none, and reheated the child's memory item on the parent's activity.
- Branch switches should restore the matching snapshot.
- Branch snapshot summaries and recent-session tails should not be raw command-only hook activity, and should not include child-session activity — scoped session listings and counts, and the scope anchor, read primary sessions only. Unscoped store totals (`cortex status`) still count every session.
- Ending a session ends its still-active children, so subagent sessions stay reachable by consolidation and event GC, both of which require `status = 'ended'`.
- Stale notes should decay out of the default state unless reinforced by actual retrieval/use.
- Resolved notes should remain cold even when retrieved, and should not trigger reflex `additionalContext`; `cortex_resolve` is the explicit close-out path.
- Writing a note whose content **opposes** an active `note:decision` on the same subject marks both sides `conflict = 1` and returns a payload naming the prior's id, subject, timestamp and text. The write always succeeds — a conflict is advisory metadata, never a rejection. A note with no subject issues no detection query at all.
- Detection is deterministic and offline: an explicit polarity flip over demonstrably shared context. A negation counts only when it **governs a predicate the other note also asserts** — "use postgres, not mysql" refines "use postgres" rather than contradicting it. Negators match raw surface forms, never stems (`stemLite('noted') === 'not'`), and a fragment of a compound is not a negator (`--no-verify`, `src/capture/no-op.ts`). An antonym flip additionally requires near-identical remaining content, so `required for rank mode` vs `optional for shadow mode` is not a contradiction. Overlap divides by the **larger** core, so a short note cannot be contained into a match.
- Contradiction detection is scope-keyed — a decision on another branch is not a contradiction of this one. Auto-supersede stays scope-blind, as it always was.
- Conflict detection runs **before** auto-supersede and vetoes it (AD-17): a contested prior stays `active` rather than being flipped to `superseded` and demoted — cooling one side of the contest at write time. The veto covers priors **already** carrying `conflict = 1`, not just those the incoming write contradicts; otherwise a later unrelated decision quietly cools one side of an open contest. Non-contested priors supersede exactly as before; demotion resumes for a subject once its contest is closed via `cortex_resolve`.
- Superseding **demotes instead of archiving** (FR-4): the predecessor's item moves one tier colder at the transition (hot→warm, warm→cold, floored at cold, pinned never touched), stays retrievable for plain and temporal queries, and renders with a `(superseded)` label wherever a note renders. Pre-1.4 rows already `archived` stay archived — forward-only, no resurrection — and since superseded items no longer reach `archived`, the archived-GC rule no longer collects them, exactly like `resolved` today. Blockers are never demoted by a decision: supersede matches `prior.kind === opts.kind` and only decisions/intents supersede at all.
- **The demotion's durable half lives in the derive layer, not in the transition write — and the derive layer is the authority when they disagree.** `deriveMemoryItemState` recomputes every non-pinned/non-archived state from the hotness score on each working-set refresh, and a freshly superseded decision scores hot-range — so a one-time `state='warm'` write would be flipped back to `hot` on the next refresh. Instead the derive rule is: a superseded item lands one tier below what its **score** would grant. Consequence, stated honestly: the transition's step from the *stored* tier is the immediate effect, and the first refresh re-settles the item at scored-tier-minus-one — for a fresh decision (stored `warm`, scoring hot-range) that means transition writes `cold` and the refresh settles `warm`. "Hot→warm" is durable; "warm→cold" is durable only when the item genuinely *scores* warm. Reinforcement (touch raises the score) caps at `warm`, decay keeps walking it down, `touchMemoryItems` preserves rather than reheats, and `stalePenalty` pushes it down like `resolved`. The transition itself demotes **exactly once** — `syncMemoryItemForNote` passes an existing item's state through for superseded notes, because `markConflict`/`clearConflictsForSubject` re-sync every note on a subject and a re-deriving sync would step the tier on every re-sync. `updateNoteStatus` runs its read→flip→sync→demote as one IMMEDIATE transaction for the same shared-database reason `insertNote` does.
- The superseded read is **trailer-scoped**, **exact-case** and **kind-guarded** (`isSupersededMemoryItem`), the full `renderedAlternatives` discipline — line-exact alone was not enough. A note whose free-form *content* contains its own `Status: superseded` line would read as retired while `notes.status` is `active`, unclearably, and the consequences exceed a label: the demote cap, the stale penalty, and exclusion from the SessionStart brief and reflex. The trailer scan (`noteTrailerLines`, moved from `render.ts` to `memory/items.ts` so `hotness.ts` can reach it under the layer direction) rejects content lines because `Subject:` always follows content; the kind guard exists because an episode's captured stderr can carry the exact line — this repo's own failing-test output does — and a fresh command-failure episode must not be demoted by its own log. The residual (a subject-less insight ending with the line) is the same bounded exposure `renderedAlternatives` documents. Only the `touchMemoryItems` SQL CASE uses substring LIKE — the resolved branch's pre-existing divergence; the derive layer re-settles any disagreement on the next refresh.
- The `(superseded)` label wins the shared slot over `(resolved)` — the resolved sniff is a substring, so a superseded note merely *mentioning* "status: resolved" would otherwise render both. `Hot:` re-attaches the label after its fixed 110-char truncation exactly as it does `[contested]`, and `Resume:` appends it — the only superseded items that can reach those hot/pinned surfaces are **pinned** ones (demotion and the derive cap stop everything else at warm), and a pin is precisely the case where the label must not be lost.
- The SessionStart brief and reflex **explicitly exclude** superseded items. `resolved` never needed that filter — it lands `cold`, outside `BRIEF_STATES` and `ACTIVE_REFLEX_STATES` — but a superseded item demotes to `warm` at best, which is *inside* both sets. Both channels inject one remembered item as settled context; a retired decision is the one thing they must never present.
- `cortex_resolve` closes a contest: resolving either side clears `conflict` on every note for that subject in scope, so the survivor stops rendering as contested. While a contest is open, resolving **by subject** is refused with both ids — the "one active note per (kind, subject)" invariant no longer holds, so `findActiveNoteBySubject` would otherwise silently resolve the newest and leave the retracted decision live. A `replacement` write skips detection; it is explicit resolution, not a new contest.
- The whole note write is one **IMMEDIATE** transaction. Detect → supersede → insert → mark is four statements, and a concurrent writer landing between them supersedes the row the write just decided to protect. Deferred is not sufficient: it takes the write lock lazily, so the read-then-write upgrade fails with `SQLITE_BUSY_SNAPSHOT`, which bypasses the busy handler — losing the veto *and* discarding the note.
- The supersede veto over contested priors is deliberately **not** scope-filtered, even though detection is. Auto-supersede is scope-blind, so scoping the veto would let a decision on one branch cool one side of an open contest on another.
- Contested items render a `[contested]` marker (3 tokens) on **every** surface that shows a note: recall, brief, state (working sections, `Current session:`, the `Hot:` highlights and the `Resume:` line), the SessionStart brief, and reflex. The unprompted channels — SessionStart brief and reflex — are named in no AC but matter most: each injects a lone remembered item as settled context, so an unmarked side of an open contest is the exact failure the marker prevents. Enumerating `renderMemoryLine` call sites is **not** sufficient to find these; `session-brief.ts` and `renderResumeCandidate` have their own renderers.
- `renderHeaderHighlights` truncates at a fixed 110 chars, which is not the output budget, so the marker is re-attached **after** truncation. Appending it beforehand loses it outright on any note past ~97 chars — silently presenting one side of a contest as settled on every SessionStart.
- The contested sniff is **line-exact** and **note-only**. `buildNoteMemoryText` always emits `Conflict: true` as its own line, so a substring match makes a note that merely discusses the flag render as contested — permanently, since `cortex_resolve` clears the column while the marker is read from text. Non-note kinds have no conflict column at all, and an episode's captured stderr can carry the phrase.
- A note carrying `alternatives` renders an indented `already rejected: a, b` line beneath it, in `recall` and `brief` **only**. Those are the two surfaces that budget line-by-line through `assembleBudgeted`; `state` budgets whole sections, and the SessionStart brief, `Resume:`, `Hot:` and reflex all truncate to a fixed width, so a continuation line there could not drop independently of its decision — which is the entire guarantee. This is the opposite call from `[contested]`, which is three tokens on an existing line and belongs everywhere.
- **Adding continuations never changes which primary lines render, at any budget.** `assembleBudgeted` runs two passes: pass 1 places every affordable primary line exactly as it always did, pass 2 spends only what is left on continuations, top-down, stopping at the first that does not fit. Dropping from the bottom alone would *not* deliver this — with `[d1, alt1, d2, alt2]` a cut landing on `d2` drops that decision and its alternatives together, and `alt1` has already spent budget `d2` needed. When nothing carries alternatives, pass 2 is a no-op and output is byte-identical to before the feature existed. This is the invariant to test, and it must be asserted against `assembleBudgeted` directly — an end-to-end budget sweep pins the shape of its fixture instead. **"No alternatives line appears while any decision is missing" is a stronger claim and is false:** pass 1 is a greedy prefix that stops at the first line too long to fit, so a lower-ranked decision can be trimmed for its own length while a higher-ranked one shows its alternatives. AC #2 is per-decision and still holds; the reader just cannot infer the trade from the output.
- The alternatives read is **trailer-scoped**, **exact-case** and **note-only** — a line-exact match anywhere in `text` is *not* enough. Three locked suites (`budget`, `kind-ordering`, `stemming`) seed decision text whose *content* contains `Alternatives:` mid-sentence; two of them detonate under a substring match (`output_tokens` +25 and +18). Worse, a note whose content holds its own `Alternatives:` **line** fabricates a rejection list for a note whose column is `NULL`, unclearably — `cortex_resolve` has nothing to clear. `noteTrailerLines` recovers the lines `buildNoteMemoryText` appended by walking back from the end and requiring `Subject, Alternatives, Conflict, Status` order; a real `Alternatives:` line always follows `Subject:`, a typed one always precedes it, and subject is mandatory for every kind but `insight`. Within the trailer it takes the **first** match: an alternative containing a newline splits into extra `Alternatives:` lines whose text the note author controls, and taking the last would let those replace the real list outright.
- `buildNoteMemoryText` collapses whitespace inside each alternative and drops empty entries. The array is joined onto one line, so an embedded newline otherwise truncated the list at the first entry and fed the reader content posing as the rest of it. `renderedAlternatives` also caps the payload, because the budget pass stops at the first continuation that does not fit — one runaway list would otherwise suppress every other decision's alternatives and leave most of the budget unspent.
- **Contested pairs are seated together; the reach differs by surface.** `recall` is a flat ranked list and groups unconditionally. `brief` and `state` sort by kind first and group **within** a kind — the common case, since detection's prior is always a decision. A cross-kind contest stays split there; seating it together would dismantle the kind ordering. Pairing is on `(scope_key, subject)` because detection is scope-keyed. Grouping **does** reorder — a counterpart is promoted past whatever ranked between the two sides, so a tight budget can keep it and drop a higher-ranked uncontested item. Only rank 0 is fixed. Safe for the gate solely because the reorder lives in `recall.ts`, never in `retrieveMemory`: the eval harness reads `top1_hit`/`recall_at_3` straight off retrieval.
- `cortex list-memory` pages the store and `cortex inspect-memory <id>` opens one item (FR-21). Both are **operator surfaces, not retrieval**: they rank nothing, budget nothing, and are the only places that show what retrieval filtered out. Two defaults invert the repo-wide convention on purpose — **no state filter (so `archived` is listed) and no scope filter (so other branches are visible)** — because a listing that hides rows cannot answer the question it exists for. Order is `created_at DESC, rowid DESC` and the criterion is **printed**, not merely implemented; the `rowid` tiebreaker is load-bearing, since seeded and same-transaction items share `created_at` to the millisecond and offset paging over a partial order silently repeats and skips rows.
- The page cap lives in `resolvePageLimit`, not in the CLI action: 20 by default, **200 maximum for every caller that goes through `listMemory`** — which is every path that renders a page. It is deliberately **not** a cap on `listMemoryItemsFiltered`, which treats an absent limit as SQLite's `LIMIT -1` because internal callers need that; the guarantee belongs to the query layer, not the store. Non-finite, zero and negative all fall back to the default, and the two guards fail differently: Commander yields raw strings, so a non-numeric `--limit` arrives as `NaN`, which better-sqlite3 rejects outright — an unguarded crash on a typo — while a negative limit is the dangerous one, since SQLite reads a negative `LIMIT` as *no limit* and would dump the whole store, the exact clause AC #1 forbids. Parse with `Number`, never `parseInt`: `parseInt` succeeds on a *prefix*, so `--limit 1e3` silently becomes 1 and never reaches the `NaN` fallback. `resolvePageOffset` clamps to `Number.MAX_SAFE_INTEGER` for the same class of reason — a larger value reaches the driver and surfaces as a raw `datatype mismatch` stack trace.
- **Stored strings are content, not output.** `notes.alternatives` and `subject` are author-supplied and reach these renderers raw, so both are collapsed onto one line and the alternatives payload is capped — the discipline `buildNoteMemoryText` and `renderedAlternatives` already apply on every other surface. Reading from the authoritative column instead of the projection must not discard the guard along with the indirection: an alternative containing a newline otherwise prints extra lines *inside the conflict section*, so a note whose `conflict` column is `false` can display `contested with <fabricated id>`. A newline in `subject` likewise forges a second listing row. `inspect-memory` also strips terminal control characters from the verbatim text — it is the first surface printing text untruncated, and `captureOutputTail` keeps ESC and lone CR — while `--json` stays byte-faithful.
- Empty filter values must narrow, never widen: `--kind ""` is a filter the operator typed, so it is passed through as an empty array (which the store reads as "match nothing"), not dropped by a truthiness test that would list the entire store. `--state` is validated against the closed set, because a typo is otherwise byte-identical to an empty store — the one question this command exists to answer. `--scope` is **repeatable rather than comma-split**: scope keys embed the worktree path and the branch ref, and git permits commas in branch names.
- `inspect-memory` reads `notes.conflict` and `notes.status` **directly** through `source_table='notes'` — the only surface that can, because `ParsedMemoryItem` carries no conflict column and every other renderer recovers the flag from projected text. It reports the column, the projection, and **`diverged` when they disagree**, rather than silently preferring either; that drift is invisible on every other surface. An item claiming `source_table='notes'` whose note row is *gone* also reports `diverged` — its projection still drives the demote cap, the stale penalty and the channel exclusions with no column left to correct it, and conflating that with "never note-backed" would blind the detector to the one drift it cannot repair. Counterparts are filtered to contested notes **in the same scope**, because detection is scope-keyed while `getActiveNotesBySubject` is not.
- The trust label describes an item's references against **its own scope's** recorded app graph, which for another scope may predate that branch's checkout — so a cross-scope `stale refs` means "stale as of what Cortex last recorded there", not "missing on disk". Inherited from `ReferenceValidator` and shared with retrieval; it matters here because this is the first surface where cross-scope items are the *point*.
- Access history has two halves with different durability, and the output says so: `access_count`/`last_accessed_at` are durable, while the per-retrieval list comes from `retrieval_log`, which `cortex gc` trims to its newest rows. The retrieval lookup joins through `json_each` on `result_ids_json` — never `LIKE '%id%'`, which matches any id merely *containing* this one — and the `json_valid` guard is load-bearing rather than defensive: `json_each` over a malformed or NULL value raises, and the raise aborts the whole query instead of skipping the row.
- Neither command creates a session, and neither calls `touchMemoryItems` — **a tool for revealing what ranking holds must not change that ranking by being used.** `inspect-memory` does refresh the current app graph and persist corrected `memory_references` statuses, exactly as the retrieval path does; that is repair of derived truth, not reinforcement. An unknown id prints to **stderr** and exits non-zero in `--json` mode too, since a caller piping JSON is precisely the one that must not read "not found" as success.
- **Deleting a `memory_items` row alone is not a deletion — the item comes back.** `backfillMemoryItems` re-inserts from `notes`, `episodes`, `project_snapshots` and `command_runs` on every `ensureCortexSchema`, which every CLI command triggers, so the item returns with its original id on the next invocation. `deleteMemoryItemCascade` therefore removes the **source row** as well, in one transaction with the item, the audit write and the contest clearing. Any delete test that does not reopen the store passes against an implementation that deletes nothing durable — that is the FR-22 analogue of FR-4's "test against the refresh, not the write".
- **The source row is not the end of the chain — three of the six source tables are themselves re-derived.** `command_runs` is rebuilt from `events` (`handleCmdEvent` reuses the event id), and `episodes` and `project_snapshots` are both rebuilt from `state` (`writeSessionSummary` and `insertState` reuse their ids), so deleting only the source row is undone exactly like deleting only the projection was. `deleteUpstreamOf` walks it. A `state` row is upstream of the other two, so deleting a `state`-backed item also removes the twin projection sharing its id. **A fixture built with `insertCommandRun`/`insertEpisode` cannot detect any of this** — it has no `events`/`state` row to be resurrected from, which is exactly why the first version of these tests passed while the guarantee was broken; build them through `handleCmdEvent` / `writeSessionSummary` / `replaceProjectState`.
- A source table with **no** deletion rule is refused, not half-deleted: dropping the item while its source survives would resurrect it and report success. `DELETABLE_SOURCE_TABLES` is exported so the preview promises exactly what the delete performs.
- `memory_references`, `memory_item_semantics` and the FTS row follow a deleted item on their own — the first two by `ON DELETE CASCADE`, the third by an AFTER DELETE trigger. `openDatabase` sets `foreign_keys = ON` explicitly, but better-sqlite3 also defaults it on, so the pragma is belt-and-braces rather than the sole guarantee; the cascades are pinned by test either way.
- **Both correction paths take the write lock up front** (`runInImmediateTransaction`). Read-then-write under a DEFERRED transaction upgrades lazily and fails with `SQLITE_BUSY_SNAPSHOT`, which bypasses the busy handler so `busy_timeout` never applies — the same reason `insertNote` and `updateNoteStatus` are IMMEDIATE. Two sessions share one database file, and the spool flush writes constantly.
- **`syncMemoryItemForNote` preserves access counters unconditionally and the tier by status.** Its upsert would otherwise write the `accessCount`/`lastAccessedAt` defaults straight over an item's real history, so a typo fix reset `access_count` to 0, reheated a cold memory and silently un-pinned a pinned one — both are `computeHotness` inputs. Tier rule: `superseded` keeps its tier (FR-4 sets it once at the transition), `resolved` re-derives to cold (the close-out contract), `active` keeps whatever it had. Every re-sync path depends on this — an edit, `markConflict`, and `clearConflictsForSubject`.
- `memory_corrections.prior_text` records the text the correction commands **consume** — `notes.content` for a note-backed item, `memory_items.text` otherwise — not the projection they produce. Recording the projection made the audit row unreplayable: feeding it back doubled the kind prefix and the trailer.
- `cortex gc` prunes `memory_corrections` older than 90 days (`CORTEX_GC_CORRECTION_DAYS`). Without that rule the table grew unbounded holding full prior text, and `delete-memory`'s "until cortex gc prunes it" — printed at the moment a user believes they deleted something — was false.
- `edit-memory` **refuses replacement text whose last non-empty line looks like a projection trailer** (`Subject:`/`Alternatives:`/`Conflict:`/`Status:`). The trailer readers walk back from the end, so such text is read back as metadata: the item renders `[contested]` or `(superseded)` while its column says otherwise, and nothing can clear it. Stories 1.3/1.4 documented this as a bounded residual reachable only by hand-authoring a note; `--file` would have made it a first-class input. A mid-text mention is inert and is allowed.
- **`memory_corrections` deliberately carries no foreign key to `memory_items`.** `ON DELETE CASCADE` would destroy the audit trail together with the item, which is exactly what "an audit trail that survives the correction" forbids; a non-cascading FK would make the delete fail outright. Absent is the only shape that works, and the DDL says so. Both edits and deletes store `prior_text`, so **deleted text stays readable until `cortex gc` prunes it** — stated plainly in the README because a user deleting a memory to make it unreadable would otherwise be wrong about what happened. Retention belongs with Story 4.6's eviction work.
- Deleting one side of a contested pair **clears the contest for that subject in the same transaction**, so the survivor stops rendering `[contested]` against a counterpart that no longer exists. The scope key is read *before* the note row is deleted, because `clearConflictsForSubject` resolves scope by joining through the note's session. Inherited limitation, already accepted: clearing is per-subject, so a three-way contest over-clears — detection produces two-note contests.
- `edit-memory` corrects a note-backed item **through its note**, then re-runs the existing projection, so the trailer (`Subject:`/`Alternatives:`/`Conflict:`/`Status:`) stays consistent with the columns. Patching `memory_items.text` directly would manufacture the exact drift `inspect-memory` reports as `diverged` — from the command meant to repair memory. Access counters and state are preserved: a correction is not a new memory.
- `delete-memory` **previews by default and acts only on `--yes`**, matching `cortex gc` — the repo-wide convention for destructive operations, and the form AC #2's "the user confirms" takes in a CLI that runs under hooks with no TTY.
- `SCHEMA_VERSION` is **5**. Per AD-11 a release gets one increment: Story 2.2 was the first R1 story to add a table, so it owns the bump and the `V5_TABLES` constant; Stories 3.1, 4.3 and 4.4 **append** their tables to that constant and leave the version alone. (4.1/4.2 were withdrawn from R1 by the 2026-07-28 course correction, so `file_cards` is never appended in R1.) Story 3.1 appended `content_digests` and did **not** touch the version — its own AC said to bump 4 → 5, which was already false when it was written.
- **An older binary now refuses a store written by a newer one (P-5), and the refusal is loud for people and silent for hooks.** `ensureCortexSchema` throws `NewerSchemaError` *before* `applySchema` touches anything. Measured before this existed: the guard was `if (currentVersion !== SCHEMA_VERSION)`, an inequality firing in both directions, so a v6 store opened by a v5 binary was silently rewritten **down** to 5 and then operated on by a build that does not know its invariants — the exact condition `doctor` already refused to name "run any cortex command" as a fix for. The narrowing to `<` is belt-and-braces: the throw is what prevents the downgrade, so a mutation restoring `!==` cannot be killed by any test, and that survivor is expected rather than a coverage gap. `doctor` is unaffected because it opens read-only and never calls `ensureCortexSchema` — which is what keeps the condition diagnosable at all.
- **The AD-12 half is not decoration.** `inject-header`, `reflect`, `flush-spool` and every `hook-entry` action swallow `NewerSchemaError` and exit 0 silently; user-invoked commands print it and exit non-zero. Measured before the guard: `hook-entry reflect-pre` dumped a raw stack trace and exited 1 — on a path that fires on **every Edit and Write**. Silence is for hooks, not for people: if the user-facing commands were also silent the refusal would be undiscoverable.
- **Content digests are recorded on the cold path, and the PostToolUse hook is not edited at all.** The read spool line already carries `file`, `agent_id` and `agent_type`, so the digest is computed when the batch is *flushed* — N-4 is satisfied structurally rather than by budget, and `hooks/claude/cortex-capture.sh` is unchanged (a test asserts it contains no hashing invocation). Consequence stated rather than hidden: **a digest describes the file as of flush time, not as of the read.** Within one batch that is safe because an edit replayed from the same spool wins the verdict; a file changed by something *outside* Cortex between read and flush records the changed bytes and will later read as unchanged. That is a real bounded imprecision, and Story 3.3 inherits it.
- `content_digests` is keyed by `(scope_key, path)` — one row per file per scope, upserted, never one row per read — and per AD-4 it is a **lookup structure that does not project into `memory_items`**, so it adds no retrieval kind and carries no AD-5 fixture obligation. It records `session_id` **and** `agent_id` because AD-16 makes refund eligibility per-session with ancestor rules; a row knowing only its scope cannot answer "did *you* read it". `read_count` accumulates because Story 3.4 orders by read frequency, which a keyed upsert cannot reconstruct afterwards.
- **The 400 bytes/file ceiling (AC #5) was met by changing the table twice, and both changes were measured rather than estimated.** A surrogate UUID `id` plus a separate unique index cost **639 bytes/file — a failing AC**. Dropping the surrogate so the stated key *is* the `PRIMARY KEY`, and making the table `WITHOUT ROWID`, brought it to 376.8 for a 130-character absolute path — but still **417.8, a breach, for this repo's longest real path (135 ch) with a real 74-character branch scope key**. Cost is a page-granularity *step* function of the whole row (scope_key + path + sha256 + mtime + agent_id), never linear in path length, and `scope_key` shares the same budget. **Story 3.2 closed it by storing the path relative to the scope root** — the repo prefix is precisely what is redundant with `scope_key`. Measured after (COUNT=500, real 74-char scope key): median read path **278.5**, p90 **376.8**, this repo's longest **376.8 PASS** (was 417.8 FAIL), repo-b's longest **376.8 PASS**. **First breach moved from 130 to 152 absolute characters — and to 135 when `agent_id` is populated**, because a subagent id shares the same row budget. So the ceiling holds for every real path in this repository and repo-b on a *primary-session* read, and is still breached for a *subagent* read of the longest paths; reducing it further means shortening `scope_key`, which is a scope-layer change. Both breach points are pinned by test so neither can move silently.
- **The flat digest index lives at `<project>/.cortex.index`, and that location is forced.** Story 2.5 moved the store to `$CORTEX_HOME`, but the hook scripts resolve every file they touch as `"$CWD/.cortex.*"` in pure bash; finding a relocated index would mean hashing a path inside `PostToolUse`, which needs sha256 in bash or a Node process, and N-4 forbids a process per tool call. This is the same architectural floor that keeps the spool, `.cortex.state` and `.cortex.agent-used` in the project root — which is why `IGNORE_ENTRIES` grew rather than shrank.
- The index is **a projection of the table, not an accumulation of batches**, and that distinction is what separates its two ACs: an index appended per flush satisfies "the flush writes it" while quietly failing "a deleted index is *fully* regenerated". It is rebuilt in full whenever a batch recorded reads or the file is missing, so deleting it costs a rebuild and never memory. Format is tab-separated `scope_key · path · sha256 · byte_size · session_id · agent_id`, LF-terminated, fixed six columns with `-` for an absent agent so `cut -f6` cannot lie. Every field is percent-escaped for tab, CR and newline: `path` is whatever the agent read and `scope_key` embeds a branch ref, so a raw tab forges a column and a raw newline forges a whole record — letting one file's line claim another file's digest.
- **AC #5's lookup cost is measured and recorded here, and the budget it names is NOT claimed as met.** `grep -F` over the index: **41.0 ms @1k records, 45.5 @10k, 58.6 @50k, 100.5 @200k** — against a process-spawn floor of ~39–42 ms on this Windows/Git Bash machine, so the marginal scan cost is ~2 / ~6.5 / ~19.6 / ~61 ms. The lookup is small. What is *not* small is the platform: `jq` alone costs ~81 ms and a plausible Story 4.5 sequence (jq + two greps + `sha256sum`) measured **214.8 ms against B-4a's 100 ms**. B-4a is formally under a PRD amendment (B-4 measured ~400 ms against ≤15 ms), which is why Story 4.5 is blocked. Reporting "within B-4a" would be a false green; the lookup number above is the deliverable, and the budget stays open.
- The index writer rewrites the **whole** projection on every qualifying flush: **1k digests → 164 KB / 6.4 ms, 10k → 1.65 MB / 29 ms, 50k → 8.3 MB / 149 ms**. Bounded by the 60-day digest GC. Note the index reintroduces some of the redundancy the relative-path change removed — on this checkout `scope_key` is 74 of ~231 bytes per line, about a third — because a consumer must be able to tell one branch's record from another's.
- The index is written **temp-file-plus-rename**, and the reason is sharper than ordinary care: a `grep` over a half-written file does not fail, it answers *wrongly*. Atomicity has no observable difference in the success case, so a mutation replacing it with a direct write survived every behavioural assertion until the write path took an injected `writeFileSync`/`renameSync` purely so the mechanism itself could be asserted.
- **A relative path key must never be re-resolved.** `path.resolve` anchors a relative input to `process.cwd()` — whatever directory the flush, CLI or MCP server happens to run in. Measured: re-running the 3.1→3.2 path migration turned `src/kept.ts` into `c:/claude code/cortex/src/kept.ts`, silently relocating every key to the process's cwd and orphaning the rows it had just repaired. `toScopeRelativeKey` returns an already-relative input untouched, and the migration additionally skips anything not absolute; the two guards are redundant on purpose, so a mutation of either alone survives.
- `content_digests` is pruned by `cortex gc` (`CORTEX_GC_DIGEST_DAYS`, default 60), dry-run by default like every destructive operation here. It shipped in 3.1 with **no** rule at all, and unbounded growth matters more than usual because the index the hot path greps on every read is a projection of it. Keyed on `recorded_at`, which the upsert refreshes on every read, so an actively-used file is never pruned however old its first read was; a pruned row costs one re-read and can never lose user-authored memory.
- Digest size is bounded by `CORTEX_DIGEST_MAX_BYTES` (default 2 MiB), decided from `statSync` **before** the bytes are read, and parsed with `Number` — never `parseInt`, which succeeds on a prefix and would read `2e6` as 2, turning a 2 MB ceiling into a 2-byte one. Past the ceiling the row keeps path and size, sets `sha256` NULL and marks `oversize`. Binary and non-UTF-8 files **are** digested: the raw `Buffer` is hashed and never decoded first, or the same bytes would not reproduce the same digest. AC #4's "never carded" is satisfied by construction — file cards were withdrawn from R1, so no carding path exists to suppress.
- **The read ledger answers exactly four verdicts (FR-6), and `changed-since` is the bucket every uncertainty falls into.** `unread`, `unchanged-since <ts>`, `changed-since <ts>`, `edited-by-you-since <ts>`, reachable through `cortex_read_ledger(paths)`, `cortex read-ledger <path...>` and `queryReadLedger`. AC #5 already qualifies `changed-since` with `missing`; two further states carry `unverifiable` because AD-6 forbids an assertion whose evidence is absent — an **oversize record** has no `sha256` to compare (Story 3.1 stores path and size only past 2 MiB), and a file that is unreadable, now oversize, or has become a directory cannot be hashed. Both are misses: they cost a re-read and can never license a false refund. `missing` is ENOENT/ENOTDIR alone; reporting a permission error as `missing` would tell the agent a file it merely cannot read no longer exists.
- **`unchanged` is asserted only after re-hashing, and both halves of that are tested.** `mtime` is recorded by Story 3.1 for reporting and is never read by the query. The two tests that matter are complementary: same mtime with different content must **not** be `unchanged` (the false refund), and a new mtime with identical content must **still be** `unchanged` — a `git checkout` or a restore rewrites mtime without touching bytes, so an mtime comparison would also destroy the feature's value in the safe direction.
- **Your own edit is checked BEFORE the content comparison, and the order is the correctness argument.** Story 3.1 records the digest at *flush* time, so the ordinary sequence — read a file, edit it, ask later — replays the read line against **post-edit** bytes: the record equals the file on disk while the agent's context holds the pre-edit content. Comparing content first therefore answered `unchanged-since`, refund-eligible, for content the agent demonstrably did not have. Measured: context `ORIGINAL`, record and disk both `EDITED`, verdict `unchanged-since`, with `sessionEditedPathAfter` returning **true** throughout — the evidence to answer correctly was in hand and the ordering skipped it. The story shipped the reverse order justified as "Cortex is holding proof the content is identical"; that proof is about the **record**, which is not what was read. `src/capture/digest.ts` had already promised the opposite in writing ("an edit replayed from the same spool wins the verdict"), so the ordering also broke a documented cross-story contract. A round-tripped edit now reports `edited-by-you-since` too: it costs a re-read, where the alternative costs a wrong skip.
- **The AD-16 ancestor-retention rule is conditional on the CONTENT being unchanged.** Retaining an ancestor's `session_id` exists so a descendant's re-read does not erase "the ancestor read this". Unconditionally, it retained the ancestor's *identity* while overwriting the ancestor's *snapshot*, so `session_id` stopped meaning "the session that produced these bytes". Measured: parent reads X, the file becomes Y, the parent's **own subagent** reads Y — the row kept `session_id = parent` with `sha256 = Y`, and the parent was told `unchanged-since`, refund-eligible and **unattributed**, about content it had never seen. That is AD-16's "says you read it when you didn't" and AD-6's "asserts unchanged without evidence" simultaneously, at the only nesting depth that exists today. `IS` rather than `=` so two oversize rows (both `sha256` NULL) compare equal instead of yielding NULL and silently taking the ELSE branch.
- **An author-supplied agent name is sanitized before it reaches a rendered verdict**, because this line's own grammar makes two characters dangerous: `;` separates qualifiers, so an `agent_type` of `general-purpose; missing` rendered `(read by general-purpose; missing)` — a qualifier no probe returned — and parentheses close and reopen the group. The second person defeats AC #6 outright: an `agent_type` of `you` rendered `(read by you)` on a read that was explicitly not the asker's, with the suite green, because the AD-16 tests assert against a name the *test* supplies. Neutralised as whole tokens, so `youtube-indexer` is untouched. Control characters are stripped rather than collapsed — `\x1b[1A\x1b[2K` in a name erases the *previous* file's verdict from a terminal.
- **A primary session is never named by its `agent_type`.** That column defaults to `'primary'`, and `inject-header` ends the session tree and creates a fresh primary on every SessionStart, so a read from *any* earlier session of the same project renders here. Measured on this repo's live store: 163 primary sessions against 9 subagents, making `read by primary` the ~18:1 majority answer — naming a role every session shares including the asker's own, and sitting one synonym from the second person the rule forbids. An earlier primary is described (`read in an earlier session`); only a genuine subagent is named.
- **Regexes matching control characters are written with escapes, never literal bytes.** Authoring one literally put a raw NUL into `src/query/read-ledger.ts` — which is exactly how `src/transports/hook-entry.ts` became invisible to ripgrep, grep and `certify_refs`'s text pass, hiding one of four copies of `findDbPath`. A literal control character is also unreviewable in a diff and does not survive a copy-paste.
- **AD-16 eligibility is `recorder ∈ ancestry(requester)`, and `edited-by-you-since` needs it twice over** — you read it (the record must be eligible) and you changed it (the edit must be *this* session's). An **ancestor's** edit is deliberately not yours: AC #4 says "the requesting session edited", so it falls through to `changed-since`. The ancestry walk uses a visited set and a depth cap rather than `parent_session_id ?? id`: depth is 2 today by construction, the shorthand is correct for exactly that shape, and its failure mode when nesting changes is a wrong "you read it" — while `parent_session_id` carries no CHECK against a cycle, which would hang the surface rather than answer it wrongly.
- The `edited-by-you-since` join is the one place `events.target` (**raw**, as the tool reported it) meets `content_digests.path` (normalized, scope-root-relative). Comparing them directly never matches and fails **silently**, degrading to a bare `changed-since`. `sessionEditedPathAfter` normalizes both sides through the same `toScopeRelativeKey` the write used; its SQL `LIKE` is a **prefilter only**, keyed on the basename because that is invariant under every transformation except case, and SQLite's `LIKE` is already ASCII-case-insensitive. A prefilter that over-matches costs nothing; one that under-matches loses the edit fact.
- The comparison is a **strict `>`** at millisecond resolution, so an edit recorded in the *same* millisecond as the read does not count — reachable in production, because a spool flush replays a whole batch in a tight loop. It degrades to `changed-since`, the miss. Loosening to `>=` would let an edit recorded *before* the read read as "you edited it since", which is a wrong attribution. Any test that just calls read-then-edit is a coin flip on this — observed failing intermittently across consecutive runs of the same suite, with a different set of tests red each time — so force the clock past the recorded stamp rather than sleeping.
- A relative path handed to the query resolves against the **scope root**, never `process.cwd()` — the substitution Story 3.2 measured silently relocating every key it touched. Both transports resolve against cwd *before* calling, because that is what someone typing a path in a shell or a tool call means; the core stays deterministic for programmatic callers. The transports also report the path **as asked**, since an absolute path burns the per-file budget on a prefix the caller already knows.
- AC #7's **20 ms p95 is measured in-process** against a 10,000-item store, which is also the real cost on the agent-facing path because the MCP server is long-lived. A **CLI** invocation cannot meet it and never could — measured end to end, `cortex read-ledger` costs **532–573 ms**, against ~48–52 ms for a bare `node -e 0` on this machine. (An earlier version of this bullet cited "~40 ms", which was Story 3.2's *process-spawn floor*, not this command: Node boot, module graph and store open dominate it by an order of magnitude.) **What the 20 ms covers is one path over a small file, and cost scales with BYTES, not rows** — hashing dominates, and `READ_LEDGER_MAX_PATHS × CORTEX_DIGEST_MAX_BYTES` bounds a single call at 40 MiB of synchronous hashing. A full-cap request over large files measures in the tens to low hundreds of milliseconds and is pinned by its own test at a deliberately loose ceiling. The perf fixture also asserts that `sessionEditedPathAfter` actually **ran** during the measurement: before the edit check moved ahead of the content comparison, a matching digest returned early and the query's only unbounded part was never on the measured path.
- The ≤30-token budget is enforced **per file** and asserted across all 24 verdict × qualifier × attribution combinations — with a **200-character** `agent_type`, not a convenient one. Every combination previously hard-coded a 15-character name while the renderer truncated only the path, so the attribution was uncapped and the line breached at 67 characters (64 tokens at 200). The path is truncated from the **left** so the filename survives, and the verdict — the answer — is never what gets cut.
- Story 3.1's flush-time-not-read-time imprecision is **inherited here, not repaired**: a file changed by something outside Cortex between the read and the flush recorded the changed bytes and reads as `unchanged-since`. The bound is the flush interval.
- `content_digests.session_id` is `ON DELETE CASCADE`, so deleting the recording session destroys a scope-wide change-detection fact. Nothing in `src/` deletes a session today — latent, not live — and it is pinned by test so a future session GC cannot quietly remove facts other sessions depend on. The degradation is at least in the safe direction: the ledger answers `unread` rather than mis-attributing.
- **Test suites that spawn POSIX tools must resolve them absolutely (`tests/posix-tools.ts`), never by bare name.** `spawnSync('bash', …)` inherits the parent's PATH, and on Windows that resolves to `C:\WINDOWS\system32\bash.exe` — the **WSL launcher**, a different OS that cannot see the Windows PATH's `jq`. Measured: launched from PowerShell instead of Git Bash, seven `digest-index` **tests** failed with `status === null` (a spawn error, not an assertion) and seven `capture-hook` tests self-skipped, so the shell/jq layer — the one `tsc` cannot see into — went unverified while the run reported green. Git dirs are searched **before** PATH on win32, and `Git/bin` **before** `Git/usr/bin`: the former is the wrapper that sets up a POSIX PATH, the latter the bare binary, and the real `cortex-capture.sh` run through `usr/bin/bash.exe` exits 0 and writes **no spool line** — AD-12's silent degradation hiding a broken harness.
- **The session brief names files this scope has already read that are still unchanged (FR-7)** — one line, up to five, ordered by `read_count`, which Story 3.1 recorded for exactly this. It is **scope-wide and never uses the second person**: `inject-header` ends the session tree and creates a fresh primary on every SessionStart, so a filter for "reads by the asking session" would leave the line permanently empty on the one surface that runs at session start. Story 3.3 hit the same wall and stopped rendering `read by primary`. The line describes the files, not the reader.
- **The verification cost is bounded by what the read will ACTUALLY cost, and both halves of that were wrong first.** "Unchanged" means re-hashing (never mtime), and this runs under **B-1 (brief ≤150 ms p95)**. (1) The meter charged `byte_size` *as recorded by Story 3.1* while the hash reads whatever is on disk **now** — measured, rows totalling 24 recorded bytes hashed 48 MiB. (2) The ceiling was gated on `found.length > 0`, so it could not fire until a file had already been verified unchanged — meaning that when *every* candidate is changed, which is the ordinary state after a pull, a rebase or a branch switch, all 24 were hashed regardless of size. The two compounded, because a file that grew is by definition *changed* and so never becomes a hit: **102 ms p95 measured against B-1's 150 ms, and 216 ms at a raised `CORTEX_DIGEST_MAX_BYTES`**, for a line that returned nothing. Now a `statSync` measures each candidate before hashing and the gate keys on `spent > 0`, which still always attempts the first candidate so a single oversized file is not silently skipped. Oversize records (`sha256 IS NULL`) are excluded in SQL — they can never be verified and would burn a candidate slot, which is only observable when the window is *scarce*, so the test sets it to exactly the number of real files. Measured after: brief p95 **16.1 ms**, ledger line ~2.8 ms.
- Scope keys whose root cannot be resolved are **dropped, not defaulted**. `resolveOnDiskPath` falls back to `path.resolve(input)` when the root is null, which anchors a stored *relative* key to `process.cwd()` — the substitution Story 3.2 measured silently relocating every key it touched. This is the first caller to feed stored relative keys back in, and on this repo's live store the project scope key already resolves to null while being one of the two keys the brief always passes.
- The line **dedupes by path**. `resolveWorkingScopeKeys` returns the preferred scope *and* the project scope, and digest paths are scope-root-relative, so one file read under both rendered twice — burning slots out of AC #1's five.
- **Each path is collapsed, capped and comma-quoted, because this was the only line in the brief that was neither collapsed nor truncated.** A filename containing a newline forged a whole `- resume:` line in the unprompted SessionStart channel (reachable on Linux/macOS/WSL, the platforms `hooks/` ships for); a lone CR overwrites the previous line on a terminal; and a comma — an ordinary filename character on *every* platform — made two real files render as three names. That is the class already bound in `digest-index`, in `inspect-memory` and by `renderReadLedgerLine`'s own `collapse()`: the rule existed and this line skipped it. Paths are elided in the **middle**, so both the disambiguating directories and the basename survive.
- **AC #2's "drops first" is enforced explicitly, not by position.** The existing loop removes the last line before the footer, so appending the ledger line there would satisfy the AC *by accident* — and any later reordering, or a `resume` line arriving after it, would break the guarantee silently with every test still green. It is removed by identity before the generic loop runs. The test sweeps every budget from 5 to 150 and asserts there is **no** budget at which the ledger line survives while `resume` has already dropped, rather than pinning one hand-picked number.
- The brief touched no filesystem before FR-7. Hashing can throw (a permission change, a vanished mount, a path that became a directory), AD-12 binds SessionStart to silence, and a brief that dies takes the notes with it — so the ledger path is wrapped and its failure costs **the line, never the brief**.
- **The session brief was a surface the gate could not see, and Story 3.4 is the story that had to close it.** `evaluateStore` computed `header` and `full_state` on every run and **asserted on neither**, and did not build the brief at all — so every guarantee this file publishes about the brief (the `[contested]` marker on unprompted channels, the superseded exclusion, the ≤150-token budget) was enforced by unit tests alone and could regress without a red build. Suites may now carry `surfaces` entries (`expect_contains` / `expect_excludes` / `max_tokens`) over `brief`, `header` and `full_state`. They fail on their own terms rather than by a baseline delta: rendered text is either right or not, and a baseline that could record a broken brief as acceptable is the state the hook exists to prevent. An unknown surface name is **refused at load**, because it would read every assertion against `undefined` — `contains` would fail loudly but `excludes` and the token budget would pass vacuously.
- **`superseded-history` could not exercise the superseded exclusion, and that is why `brief-surface` exists.** That suite seeds its retired decision in state `cold`, and `BRIEF_STATES` is pinned/hot/warm — so the *state* filter removes it before `isSupersededMemoryItem` is ever consulted. Measured: deleting the superseded guard from the brief left the whole gate green against it. The guard is load-bearing precisely at `warm`, which is where FR-4 says a superseded decision lands, so `brief-surface.json` seeds it warm. Each brief assertion also asserts a surviving line is **present**, or a brief that rendered nothing at all would satisfy every `expect_excludes` and pass.
- **The FR-7 line itself is deliberately NOT gated, and that is a stated limit rather than covered ground.** The harness builds the brief with `includeReadLedger: false`, because the line names files that must exist on disk with matching hashes and a seeded in-memory scenario cannot stage that — leaving it on would make a suite pass or fail by what happened to be checked out. The line is covered by unit tests only; what now gates is everything else the brief renders.
- **The mechanism gates only what a fixture actually binds, and two of those bindings were decoration until measured.** `max_tokens: 150` against a seeded brief of 36–77 tokens can never fire, so deleting the whole budget-enforcement loop left the gate green; a `SurfaceFixture` may now supply its own `budget`, and `brief-surface` renders at 44 where the budget genuinely binds. Likewise `expect_excludes: ["(superseded)"]` on the brief could never fire — the brief has its own renderer and emits that label nowhere — so the load-bearing assertion is that the retired decision's *text* is absent while the survivor's is present. `full_state` asserts the opposite: the superseded item **is** there with its label (FR-4), which locks the contrast between the two surfaces rather than one side of it.
- **A surface entry that asserts nothing is refused at load**, the rule `loadSuite` already applied to `fixtures: []` and had not applied to the new fixture type — `{surface:'brief'}` and empty assertion arrays were all green.
- **A first baseline reports the failing fixtures it is about to bake in.** `findFixtureRegressions` compares against the *previous* baseline and also *skips* any fixture the baseline records as failing ("the author accepted it deliberately"), so a brand-new suite could enter the locked set with a permanently-excused assertion and no warning. Measured on the suite added by this very story: a needle missing four words of the rendered text failed on arrival, was written into its own baseline as `passed: false`, and every recall assertion in it was excused forever while `npm run gate` printed `ok`.
- **The token ledger's credit side was withdrawn, and that withdrawal is FR-8's deliverable.** Before Story 3.5 the ledger had seven write sites; six wrote `'spent'` and exactly one wrote `'saved'` — `estimateTokens(JSON.stringify(events)) - estimateTokens(summary)` in `writeSessionSummary`. That single line was the entire `Saved: 657.6k` and `Efficiency: 93%` the product displayed. It credits the difference between a session summary and pasting every captured event into the context as raw JSON: a baseline no agent would ever have paid, which AC #3 names exactly ("no modeled or counterfactual credit"). **The deeper reason is that the quantity was never a token saving at all** — `events` is internal capture and is never injected; the injecting surfaces render *memory items*. Consolidation compresses the database, and this is a token ledger, so measuring the pruned bytes more precisely would only have produced an accurate number for the wrong quantity. Storage compression shows up honestly in the `Database:`/`WAL:` lines.
- **`saved` and `unrealized` rows are refused without evidence.** `evidence_kind` / `evidence_ref` / `evidence_size` carry the three shapes AC #2 names — file + byte size for an avoided read, output size for an avoided command, result count for an avoided search — and `insertLedgerEntry` throws rather than writing credit that cannot be checked. Enforced in the store method rather than by a table CHECK, because adding one to a populated table means a full rebuild in SQLite; the trade-off is real and stated, since a hand-written INSERT bypasses it — which `cortex gc` does.
- **The GC rollup carries evidence forward in aggregate**, or a verified saving silently becomes an unverifiable one after 14 days and the credit side decays back into the number FR-8 just retired. Per-row evidence cannot survive aggregation but its *sum* is the meaningful quantity (total bytes actually avoided), so the group includes `evidence_kind` — a rollup of avoided reads is not interchangeable with one of avoided commands — and `evidence_ref` records how many rows were folded rather than pretending to name one file.
- `direction` is `injected | saved | unrealized | estimated`. `spent` → `injected` is a data migration (no CHECK constraint on the column) that **must cover `type='rollup'` rows too**, since `cortex gc` aggregates `GROUP BY session_id, direction` and a rollup left on the old value forms a second parallel total no query adds up. The retired consolidation credit moves to `estimated`: kept for history, never counted, because destroying an audit trail is not this repo's answer to a bad number.
- **`unrealized` is an observed decline, never an inferred one** (AC #6). Cortex answered `unchanged-since` and refund-eligible for a path — recorded as an `offer:read` row — and the agent then read that file anyway. Both halves are evidence. The offer is **consumed** on use, so a loop reading one file ten times books one decline rather than ten, and offers are **opt-in** (`recordOffers`) so `knownUnchangedFiles` — which the session brief runs on every SessionStart — cannot manufacture offers to Cortex from Cortex and then count the agent as declining them. Reported separately from savings, because folding them hides the capability-versus-adoption gap the figure exists to expose. **Consuming the offer and booking the decline is one transaction**: as two operations a failure between them destroyed the offer and recorded nothing — unrecoverably, since the offer is gone. Moving offers out of `token_ledger` fixed AD-8's append-only violation and did *not* fix this; they are separate defects, and reporting the first as covering both is how the second survived a round of review.
- **AD-15's hot-path credit path ships with no live producer, and that is stated rather than left to look like coverage.** A `tool: 'credit'` spool line carries its own evidence and is booked by the flush under the same exactly-once claim as every other line; an incomplete record is dropped rather than booked at a default, because "a lost spool record results in no credit rather than a reconstructed one" applies equally to a partial one. `parseCreditNumber` uses `Number` with a `/^\d+$/` guard — `parseInt('12abc')` is 12, which would book credit from a malformed line, the third time this repo has had to say so. What would *produce* these records is verified read substitution (Story 4.5), which is blocked on the B-4a amendment.
- **`Saved: 0` is the honest state and `cortex stats` says why.** A bare negative `Net` misleads in the opposite direction — that Cortex returns nothing — when the truth is that the credit-producing mechanism (verified read substitution, Story 4.5) has not shipped. The explanation names the missing *mechanism*, not just missing evidence, and is printed whenever `Saved` is zero rather than only when something was spent — a store with no spend would otherwise show a bare `Efficiency: 0%`, which reads as a measured verdict instead of an absence of measurement. `formatTokens` also gained a negative branch: `Net` was structurally positive until this story, so `-45827` printed raw beside a screen of `45.8k`s.
- **Inline `--` comments inside a `CREATE TABLE` make the table permanently un-alterable.** SQLite stores the original DDL text and re-parses it during `ALTER TABLE … DROP COLUMN`; with comments inside the definition that re-parse fails with `error in table token_ledger after drop column: incomplete input`. Found because a migration test downgrades a *real* store to its pre-migration shape rather than hand-building a fake two-table database — the first attempt at that fake died on `sessions.parent_session_id` when the index pass ran, which is its own lesson. Column documentation belongs in the TypeScript docstring. (Backticks are separately fatal there: the DDL lives in a template literal, which Story 3.1 already paid to learn.)
- `cortex install` writes hook scripts, hook wiring, MCP registration and ignore entries, then **runs the diagnostic and exits with its verdict** (FR-26). `install-hooks` is an alias, not a separate path — eight fix strings and the README named it, and every pre-stamp hook is repaired by running exactly that; renaming without the alias would leave the diagnostic naming a command that does not exist. Note the alias widens what that name does: it now writes settings, not just scripts.
- **`install` and `doctor` share `REQUIRED_WIRING`.** What one writes is what the other checks for, by construction. Two constants would drift, and the failure that produces — a correct installation reporting itself broken — is the one thing an installer/diagnostic pair must not do. The wiring test asserts against `commandSatisfiesWiring`, not a literal string, so a drift cannot pass.
- **Idempotency is byte-identity, not a message.** A second run must leave every file it can touch unchanged — asserting only that it printed `Nothing changed` passes against an installer that rewrites identical content, which still churns mtimes, backups and the user's settings formatting. Presence of an existing wiring is decided by `commandSatisfiesWiring`, never string equality: a user who re-quoted the path or moved the hooks directory already works, and appending a second entry doubles every hook invocation.
- **"Modified" is established by re-matching the template, not by the stamp.** The stamp says which template a script came from; `installedMatchesTemplate` builds one regex over the whole template — placeholders as capture groups, repeats as backreferences — so the file is recognised as ours whatever paths it carries. A repeated placeholder whose values disagree is an edit. Verdicts: `unmodified` overwrite, `modified` **refuse without `--force`**, `unknown` back up and overwrite. `unknown` must not refuse: every pre-2.3 hook is unstamped and `doctor` names this command as their fix, so refusing there would break the documented repair path for the most common install there is.
- Settings writes **merge, never replace**; refuse a file that does not parse rather than clobbering it; land via temp-file-plus-rename; and back up before the **first** modification only, so a no-op run does not churn the backup. An existing `cortex` MCP entry is left alone — it may point at a checkout the user prefers. Formatting is not preserved (`JSON.stringify` re-serialises and drops comments); the README says so and the `.bak` is the mitigation.
- **Detecting that something is wired is not checking that the wiring is right.** `commandSatisfiesWiring` answers presence; `install` must also *repair* — a `PostToolUse` matcher that lost `Agent`, or a `SessionStart` command naming a Node that moved, were left untouched while the run reported success, and `doctor` named this command as the fix for a condition it could not fix. Both are now rewritten in place, and a second run converges to `unchanged`.
- **Idempotency is per-configuration, not per-file.** Claude Code merges `<project>/.claude/settings.json`, `settings.local.json` and `~/.claude/settings.json`. Writing an entry while an equivalent one lives in another file does not replace it — both fire, doubling every spool line, reflex and flush, invisibly to `install` and `doctor` alike. The merge reads the other files and skips events they already satisfy.
- **The template match constrains what a capture may contain, not just where it ends.** `([^\n]+?)` accepted any edit that left the surrounding literal text intact — closing the quote, adding a command and reopening it read as `unmodified`, so the script was overwritten with no refusal and no backup, which is exactly what AC #3 forbids. Path placeholders always sit inside double quotes, so the capture excludes `"`. Exposure was uneven and therefore hard to reason about: `cortex-reflect.sh` was safe only because it repeats `__CORTEX_NODE__` and the backreference forced agreement. **Any** overwrite of existing content now keeps a `.bak`, not only the `unknown` and `--force` paths.
- Hook scripts are written **LF**, never with the template's line endings. There is no `.gitattributes`, so a Windows checkout has CRLF templates — and a CRLF script was written and reported fully current, because every validator normalises before comparing and so structurally cannot see it. Git Bash tolerates CRLF; bash on Linux, macOS and WSL does not, and `package.json` ships `hooks/`.
- A hooks directory containing `$`, a backtick or a backslash is **refused**. Double quotes do not protect those, so the wiring would resolve elsewhere while `doctor` reported it healthy — it reads the literal string and finds the file at the literal path. `$(...)` would execute on every hook fire. Refusing beats guessing which shell the host uses.
- Every filesystem step runs through a guard that turns a throw into a `refused` action. `readJson` was guarded and nothing else was, so a `.gitignore` that is a directory threw `EISDIR` out of `runInstall` *after* the scripts and settings were written, and the caller printed a bare errno with no path under a summary claiming nothing was left half-done.
- An outcome must be computed from state the action has not yet changed: reading `existsSync` **after** the write reported `created` files as `updated` and made `--dry-run` disagree with the real run. The same rule applies to prose — the detail line reports the events actually wired, not `REQUIRED_WIRING.length`, and a dry run says a backup *would be* saved rather than claiming it was.
- `--scope` is validated against the closed set and `--codex` is refused outright. A scope typo silently fell back to `user`, writing the home settings file for someone who asked for project scope; `--codex` redirected only the hooks directory, so it rewrote **Claude Code's** settings to run hooks out of `~/.codex/hooks`.
- `--json` embeds the diagnostic. The exit code comes from `doctor`, so a payload showing `refusals: 0` exiting 1 with no report anywhere was unreadable for the one consumer that cannot see the table.
- `install` does **not** create the store or engage Cortex — AC #1 enumerates four actions and those are not among them — so a fresh project fails the diagnostic on `engagement` and `database`. When those are the only failures the command says so explicitly, because a bare red report after a successful install reads as a broken install.
- The store lives at `$CORTEX_HOME/projects/<label>-<id>/cortex.db`, `CORTEX_HOME` defaulting to `~/.cortex` (FR-24, AD-10). `<id>` is sha256-16 of the **absolute realpath** of `git rev-parse --git-common-dir`; `<label>` is cosmetic and derived from the **same** input, never from the worktree basename — a worktree-derived label gives two worktrees identical ids and different directories, which is two stores with every hash assertion still green. Realpath is not `path.resolve`: measured on win32, `path.resolve` keeps `c:\repo` as typed where the canonical form is `C:\repo`, and resolves a junction to the link rather than its target. Either splits one repository into two stores.
- **The spool, `.cortex.state` and `.cortex.agent-used` deliberately do not move.** `cortex-capture.sh` computes them in pure bash from the payload's `$CWD`; relocating them means hashing a path inside `PostToolUse`, which needs either sha256 in bash or a Node process — and N-4 forbids a process per tool call. This is an architectural floor, not a deferral, and it is why `IGNORE_ENTRIES` does not shrink. `.cortex.db` stays on that list too, because AC #3 leaves the original in the project root indefinitely.
- **Migration is `VACUUM INTO`, never a file copy.** Measured on SQLite 3.51.3: copying `.cortex.db` alone out of a live WAL store produced a database in which *the table did not exist* — every row was still in the `-wal` sidecar. That is Risk R-4 (unrecoverable memory loss) reachable in three obvious lines. `VACUUM INTO` folds the WAL in, emits one clean file with no sidecars, runs from a read-only connection, and **refuses an existing destination**, which is a race guard for free. Verification re-opens the copy *from disk* — never through the connection that wrote it — and checks `integrity_check`, `schema_version`, and the row counts of `memory_items`, `notes`, `sessions`, `events`. The copy lands on a `.migrating-*` temp name and is renamed in only after passing. **Nothing in this module deletes a project-root original**; AC #3 requires it to survive until the user removes it. Adoption does delete the store it has just copied and verified — that is what makes it a move — and that is the only deletion here.
- **The WAL test must take its naive-copy comparison _before_ closing the source.** `db.close()` checkpoints the WAL into the main file, so a `copyFileSync` taken afterwards captures every row and the test congratulates the implementation it exists to reject.
- **`openProjectStore` is the single path every transport opens through** — resolve, migrate, open, record the anchor. The last two are only correct as a pair: a store opened without `recordStoreIdentityMeta` never gets a `root_commit_oid`, and adoption matches on exactly that column, so a hand-rolled resolve-and-open produces a working store that can never be recovered after a move — invisible until the day it matters. There were four store-path derivations before this story — three named `findDbPath`, plus an inline join in `doctor.ts` — and one of the three lives in `hook-entry.ts` where **text search cannot see it**: that file carries a raw NUL byte, so ripgrep, grep and `certify_refs`'s text pass all classify it as binary and skip it silently (`rg -n` finds two, `rg -na` finds three).
- `recordStoreIdentityMeta` **reads the column before resolving the anchor**, never the reverse: it runs on every open and `readRootCommitOid` spawns git. The anchor itself is a memoized thunk on `StoreIdentity` rather than a field for the same reason — combining `--show-toplevel` and `--git-common-dir` into one `rev-parse` and deferring `rev-list` took resolution from ~176 ms to ~64 ms, and process spawn dominates on win32.
- The root-commit anchor **sorts and joins every root commit**. `git rev-list --max-parents=0 HEAD` returns all of them in traversal order for merged or grafted histories, so taking the first is not an identity. An empty repository has no HEAD, no anchor, and no adoption — a silent degradation, not an error.
- **`adoptStore` uses `VACUUM INTO` too, not a rename.** It shipped as `fs.renameSync` on `cortex.db` alone, which abandons `-wal`/`-shm` — and a store whose last writer did not close cleanly keeps its rows there. Measured: **50 rows readable in place, `no such table` after the rename.** Total silent loss on the one command whose purpose is to rescue memory, and unrecoverable, because the abandoned directory then holds no `cortex.db` for the scan to find. Removal of the source is best-effort *after* verification: a locked file must never turn a completed adoption into a reported failure.
- **Adoption must survive the store existing, not just survive migration.** Deferring migration is half the fix — opening the store *creates* it, so `findAdoptionCandidates`' "a store already exists here" short-circuit killed the offer one hook later anyway. A store an ambient start creates while a candidate is waiting carries `adoption_pending`; the scan keeps asking while it is set, `adoptStore` replaces such a placeholder, and it refuses when the placeholder has recorded **notes** of its own rather than discarding them. Notes, not `memory_items` or sessions: any ambient start writes a session and a branch snapshot, and the snapshot projects into `memory_items`, so testing those would refuse every adoption the moment a single hook fired.
- **The legacy search order is main-worktree, then repository root, then cwd — and all three positions are defects that were found.** Every worktree resolves to one store, but the pre-relocation build gave each its own `.cortex.db`, so taking the current worktree's file first migrated a linked worktree's small store and permanently shadowed the main checkout's real one (measured: 60 notes replaced by 0, not recovered by later running from main). Root before cwd because the old build wrote `<repo>/src/.cortex.db` whenever it ran from a subdirectory.
- **The migration verdict is recorded in the store, because otherwise nothing reads it.** `MigrationOutcome` was computed and discarded by every caller: a failure left an empty store, the destination now existed so it was never retried, and `doctor` inferred "migrated" from the coexistence of a legacy file and a store — then told the user to delete the only surviving copy of their memory. `migrated_from` and `migration_failed` make the diagnosis evidence-based; the failure row is a `fail` whose fix begins "Do NOT delete the original".
- **A source must look like a *Cortex* store, not merely like SQLite.** `verifyStoreCopy` compares `schema_version` and four row counts, and each read returns `null` when the table is absent — so for an unrelated database every comparison is `null === null` and the copy verifies vacuously. An unrelated SQLite file at `<project>/.cortex.db` was copied, reported verified, and installed as the project's store.
- `CORTEX_HOME` is used **trimmed**, and a relative value resolves against the user home rather than cwd. Testing `override.trim()` while resolving `override` turned a trailing newline from a shell export into a relative path segment — a home nested under cwd with an embedded drive colon, which `cortex store` printed at exit 0. Cwd-relative resolution fans one repository across several homes, since hooks, the MCP server and manual runs all have different working directories.
- Identity retries the `rev-parse` **once**. The runner cannot distinguish "not a repository" from "git could not be spawned this instant", and degrading *inside* a repository means computing a cwd-derived id and opening a different store — memory written in that window is stranded where nothing will look again. Surfaced as a one-in-five flake in the two-clones test before it was a hypothesis.
- **Adoption is offered, never performed ambiently.** AC #4 says "offered … rather than starting empty", but the path it names is SessionStart, where AD-12 forbids blocking, printing or asking. So detection is silent and free, `cortex doctor` and `cortex store` report the candidate, and `cortex adopt` performs it — preview by default, `--yes` to move, matching `gc` and `delete-memory`. Adoption **moves** the store and rewrites `root_path`, because leaving the source would keep it matching as a candidate forever and `doctor` would keep offering an adoption already done.
- **The WAL was never unbounded; it was never *shrunk*.** `wal_autocheckpoint` is 1000 pages by default and does bound it, but the passive checkpoint it runs only resets the log for reuse — measured, 4,128,272 bytes before and after — so the file parks at its high-water mark forever. Only `TRUNCATE` returns the space, and doing so on this repository's own store reclaimed 4.13 MB while the database grew 24 KB. FR-25's real content is the truncation, not the bound.
- **`close()` already checkpoints, and on an ordinary drain better-sqlite3 calls it for you.** Measured both ways: a 4 MB WAL becomes 0 on `db.close()`, *and* removing the close wiring from all three transports still leaves an ordinary command checkpointing, because the destructor runs. So the wiring is redundant on the common path and load-bearing only on `process.exit()`, an uncaught error, and a signal — where the WAL was measured parked at 12,405,352 bytes. An earlier version of this bullet claimed the OS tears the handle down without checkpointing; a reviewer measured that false. The consequence for testing is that only the POSIX signal path can *observe* the wiring; on win32 `child.kill()` is `TerminateProcess` and runs no handler, so the per-transport assertions there are an inventory against a fourth transport being added without one, not proof the three work. `closeAllProjectStores` is registered on `process.on('exit')` by each transport rather than after each command, because closing per command breaks the in-process test suite on win32, where an open handle blocks file removal — the hazard Story 2.5 had to split a test for.
- **A `busy` checkpoint is ordinary, and must never be paid for by waiting.** A connection *inside a transaction* blocks reclaiming the file while the frames still move (measured `{busy:1, checkpointed:242}`). An **idle** connection does not: there is no `.iterate(` anywhere in `src/`, so no long-lived read cursor exists, and the earlier claim that the MCP server "holds a read for the whole session" was measured false — the real cause is a transient writer, most often the backgrounded spool flush. Critically, `TRUNCATE` is RESTART-plus-truncate and RESTART invokes the busy handler, so inheriting `openDatabase`'s `busy_timeout = 5000` made every checkpoint a five-second stall: **5518 ms measured**, reaching `reflect-pre` through the exit handler — the exact path the design excluded, ungated by `CORTEX_WAL_MAX_BYTES` and unaffected by `cortex_disengage`. `checkpointWal` drops the timeout to zero for the duration (7 ms, same frames moved) and restores it after. Asserting `walSize === 0` after any checkpoint is a flake generator; assert it only where no other connection is open, and assert the *duration* — the suite already contained a six-second test nobody questioned.
- The mid-session ceiling is `CORTEX_WAL_MAX_BYTES` (default 4 MiB), parsed with `Number`, **not** `parseInt` like `gc`'s neighbouring `envNumber` — `parseInt('4e6')` is 4, which would turn a 4 MB ceiling into a 4-byte one that checkpoints on every call. It is checked by `statSync` on the sidecar, never by a query, because opening the database to ask would create the file being measured.
- **"Blocks no hook" is structural, not budgeted.** `PostToolUse` appends in pure bash and reaches `flush-spool` only through a subshell it backgrounds and does not wait for, so the checkpoint there is off the critical path by construction. The other call site is `end-of-turn`; `reflect-pre` is deliberately excluded because it fires on every Edit and Write.
- `cortex doctor` **diagnoses the store that exists, not the one this build prefers**: before migration runs, the memory is still at the project-root path, and reporting `database does not exist` would be a red failure over a fully readable store sitting right there — the diagnostic announcing memory loss at the precise moment there is none. It also gained the one subprocess it spawns (`git rev-parse`), which is narrowed in the module docstring rather than left standing as "no process is spawned": store identity has no non-git definition, so the alternative is a missing check, not a purer diagnostic.
- **`CORTEX_HOME` is the test-hermeticity boundary, enforced globally.** `tests/setup-cortex-home.ts` runs via `setupFiles` and points it at a temp directory for the whole run. Without it every test that runs a CLI command writes into the developer's real `~/.cortex` — measured at **163 directories** from a single suite run before the guard existed. Story 2.4 hit the same class once (an installer test wrote the real `~/.claude/settings.json`) and answered it with per-test discipline; this is the chokepoint version, because per-test discipline only protects tests someone remembered to write it into, and every test that leaked here predated the store being movable. `tests/hermeticity.test.ts` asserts the guard is in force *and* that removing it would really fall back to the real home, so the setup file cannot be quietly retired.
- A fixture that builds two repositories with identical content in the same second gives them the **same root-commit OID** — same tree, message, author and timestamp hash to one commit — which silently made "an unrelated repository is not an adoption candidate" pass or fail on clock luck. Repo fixtures must differ in content.
- `cortex doctor` diagnoses **the configuration that exists, not the one the installer would have written** (FR-23). It reads the settings files Claude Code merges, extracts the wired commands, and checks those — so a hooks directory the user moved, an interpreter given as a bare word, and a `~`-prefixed script path are all diagnosed as configured. Exit 1 on any `fail`, 0 otherwise; `warn` never fails the run, because a project deliberately disengaged via `cortex_disengage` is a supported state and would otherwise make the command useless in CI.
- **A diagnostic must not repair what it is checking.** `doctor` opens the store through `openDatabaseReadOnly` (`readonly`, `fileMustExist`) and never calls `ensureCortexSchema`: the normal path migrates `schema_version` to the value the check compares against, so a version mismatch could never be observed, and `openDatabase` alone would *create* an empty store for a user who has none. It also creates no session, writes no engagement state, and does not flush the spool — the rule `list-memory`/`inspect-memory` established, binding harder here.
- **It is not literally write-free, and the docs say so rather than hiding it.** Reading a **WAL** database materialises its `-shm`/`-wal` sidecars when absent; `readonly: true` prevents content writes, not sidecar creation. Opening `immutable=1` would avoid it and read past the WAL, which risks reporting a stale `schema_version` — a wrong answer, not a tidier one. The first non-mutation test ran only against a project with **no store**, so the single path that writes was the one path it never exercised; the test now asserts the real sidecar set against a real WAL store. Same trap as FR-4's "test against the refresh, not the write".
- **Wiring and presence must meet on the same path.** Wiring matches a command by the script's **basename**, so checking presence only inside the directory derived from the *first* wired command let a hook pointing at a directory that does not exist report fully healthy. Presence is checked at **every wired path** plus the resolved hooks directory.
- **A check may not assert a positive fact about a file it never opened.** With no script on disk, `hook-substitution` and `hook-currency` fell through to their pass branches and reported "no unsubstituted placeholders" and "installed scripts match the templates shipped by this build" — two of the nine things AC #1 names, reported as verified when nothing was verified. Both now report `not checked`.
- **The stamp is the only thing read from an installed script, so it cannot detect a gutted one.** Three scripts replaced with `exit 0` carrying valid stamps passed every check that inspects them. `extractBakedPaths` returning nothing for a script whose template contains `__CORTEX_NODE__` means the invocation line is gone — that is the gutted-hook detector, and "no baked path at all" is a `fail`, never a `warn`: no path is strictly worse than a missing one.
- The `PostToolUse` **matcher** is checked, not just the command. A matcher that has lost `Agent` breaks subagent capture exactly as a stale script does; without this, a user who hits the currency failure, re-copies the scripts by hand instead of running `cortex install` gets a green currency row and dead subagent capture — `doctor`'s own fix turning a detectable failure into an undetectable one. `warn`, not `fail`, because narrowing the matcher can be deliberate and must not break CI.
- **A named fix that is wrong is worse than a generic one.** For a store from a *newer* build the fix names upgrading the package, never "run any cortex command" — that path rewrites `schema_version` **down**, destroying the evidence just reported. A corrupt store names moving it aside, not file permissions. A template shipping without the stamp placeholder says re-installing cannot help, because the installer has nothing to substitute. AC #3 only requires a fix to be *present*; presence is not correctness.
- Reads that touch user-controlled paths are guarded: `.cortex.state` as a directory threw `EISDIR` out of `runDoctor` and took the whole report with it. Malformed `.mcp.json`/`~/.claude.json` are **reported**, not swallowed — the old message told users to add a registration that was already sitting in the file that would not parse. `~/.claude.json`'s project key is matched normalised, since the same project is recorded with either separator and either case.
- `PATH` parsing accepts what the shell accepts: quoted entries (`cmd.exe` strips them) and an empty `PATHEXT` (which Windows treats as unset — `??` alone keeps the empty string and resolves every `.exe` to null). Hook paths expand `~` **and** `$CLAUDE_PROJECT_DIR`, Claude Code's documented project-relative form.
- The spool check reads `<project>/.cortex.spool.jsonl` — the literal `cortex-capture.sh` writes — **not** `deriveSpoolPath`, which honours `CORTEX_SPOOL_DIR`. With that variable set the two halves disagree and the check reported "nothing pending" over a backlog no flush would collect; the divergence is now its own warning.
- **Hook currency is a content digest, not a version number.** `install-hooks` stamps each installed script with `# cortex-hook-template: <sha256-16>` of the template it rendered (line endings normalised, placeholders intact); `doctor` recomputes from the template the running build ships. A number someone must remember to bump fails in exactly the shape this check exists to catch — a hook that is stale while everything about it looks fine. **Absent stamp counts as stale**, which is every install predating the stamp, all of which genuinely do predate the current template.
- Wiring is matched against a command's **tokens, not a raw substring**. The wiring `install` writes quotes the script path (`bash "…/cortex-reflect.sh" reflect-pre`), so a `cortex-reflect.sh reflect-pre` needle never matches the canonical wiring and reports a correct installation as unwired. `UserPromptSubmit` also accepts a reflect wiring with no action argument, because `cortex-reflect.sh` runs `ACTION="${1:-reflect-prompt}"`.
- `jq` and the hook interpreter are **resolved on `PATH`, never executed** — which keeps B-7's 3-second budget structural rather than tuned on a platform where `bash -c 'exit 0'` alone costs ~36 ms, and makes the negative cases testable by pointing `PATH` at a fixture directory. Stated limit: a present-but-broken `jq` resolves and reports available. Resolution honours `PATHEXT` on Windows and tries the lowercase extension first, so a file named `bash.exe` is not reported as `bash.EXE`. **A POSIX-absolute interpreter that does not exist on win32 falls back to resolving its basename on PATH** (N-6): `which bash` under Git Bash answers `/usr/bin/bash`, which Node resolves against the drive root and does not find, so `existsSync` on the configured interpreter reports it missing on the exact platform the user runs.
- Detail and fix strings interpolate settings paths, script names and JSON parser messages — all from user-controlled files — so the renderer collapses each onto one line. A newline would otherwise forge a check row and a lone CR would let one detail overwrite the row above it; `--json` stays byte-faithful.
- The UserPromptSubmit hook may add a one-line consult hint **at most once per session** for memory-relevant prompts; there is no PreToolUse gate. Route/state/recall/brief/engage or topic-based validate-memory suppresses it.
- The Stop hook nudges (`decision:block`) only when a subagent ran this turn AND suggest-notes returns high-confidence candidates, embedding them; otherwise it is silent. `CORTEX_STOP_NUDGE=off` disables it.
- Per-tool-call capture must not spawn Node: PostToolUse appends to the spool; flush happens at turn end, the 256 KiB threshold, or next session start, exactly once per batch (atomic claim + processed marker).
- Prompt reflex should not inject memory facts from UserPromptSubmit text.

## When To Use Cortex

**Cortex is ambient for trivial new work.** For non-trivial familiar work, recurring bugs, resumed features, and systems with prior decisions, consult Cortex before planning or tool use. This is not an always-call-`cortex_state` ritual: prefer `cortex_recall(topic)` for a known area, `cortex_state` for broad resumptions, and `cortex_route` when you need the capability map.

Available tools:

- `cortex_route` — compact capability map and routing guidance.
- `cortex_engage` — re-enable Cortex capture after `cortex_disengage`.
- `cortex_state` — explicit state: current-session load-bearing notes, top-scored notes, branch snapshot, last-session tail; empty state returns next-step guidance.
- `cortex_note(kind, content, ...)` — durable memory. `kind` is one of `decision` (include `alternatives`), `insight`, `blocker`, `intent`, `focus`. Reserve for load-bearing items; skip routine progress.
- `cortex_resolve(note_id | subject, status?, replacement?)` — close out a note as resolved/superseded; with `replacement`, supersede and write the updated note in one step.
- `cortex_suggest_notes` — review proposed load-bearing notes from the current session without writing them.
- `cortex_validate_memory(topic?)` — audit retrieved or recent memories against the current checkout without deleting notes. A topic-based call counts as Cortex consultation for hook gate suppression.
- `cortex_recall(topic)` — explicit search over notes/snapshots/summaries/episodes when prior work may matter; use proactively for familiar non-trivial areas, recurring bugs, resumed features, and systems with prior decisions.
- `cortex_brief(topic)` — compact topical context to paste into a subagent prompt. Call it yourself; don't ask subagents to call it.
- `cortex_summarize` — checkpoint a dense session so the next one resumes gracefully.
- `cortex_read_ledger(paths)` — before re-reading files, ask whether you already read them and whether they changed. Four verdicts, produced by re-hashing; a read by a sibling or descendant session is reported and attributed, never as "you read it".
- `cortex_disengage` — turn capture and reflex off for the current session.

Anti-patterns (still apply once engaged):
- Don't write notes for routine acknowledgments, task tracking, or anything obvious from code/git.
- Don't re-call `cortex_state` multiple times per session.
- Don't call `cortex_summarize` for throwaway sessions.
- Don't tell the model to perform startup memory rituals; hook wiring owns ambient capture.

## Verification
- Run `npm run build`
- Run `npm run lint`
- Run `npx vitest run`
- Run `npm run gate` — every locked suite against its baseline in one command, plus AD-5 kind coverage. Names the suite and metric and exits non-zero on: a negative `top1_hit`/`recall_at_3` delta, a positive `output_tokens` delta, a failing fixture assertion, a suite with no baseline, a **baseline with no suite** (a deleted suite must not silently stop gating), a baseline **missing** a metric (absent values compare as `NaN`, which would otherwise un-gate it), a suite that asserts nothing, or an unexercised registered kind. `noise_count` and `stale_count` are reported, not gated. CI runs it on every push. (`evaluate --suite … --compare …` remains the single-suite human view; it always exits 0 and is not a gate.)
- Baselines in `eval/baselines/` and `eval/kind-coverage.json` are locked artifacts. Change one via `cortex eval-gate --regenerate-baseline <suite>` with a `Baseline-Regenerated: <reason>` line in the body of the commit that makes the change; CI rejects it otherwise. Regenerating is never the way to turn a red gate green.
- A change introducing a new `memory_items` kind must add a locked fixture exercising it in the same change (AD-5). `eval/kind-coverage.json` grandfathers the kinds that predate the gate; adding to that list is not how to pass it.
- Run `cortex doctor` (built) for the live installation — it checks the wiring, hook currency, store and MCP registration in one command and exits non-zero on any failure
- If the change affects real Claude usage, verify:
  - `~/.claude/settings.json`
  - `~/.claude/hooks/cortex-capture.sh`, `cortex-reflect.sh`, `cortex-end-of-turn.sh` (installed via `cortex install-hooks --claude`)
  - the live path Claude uses for the Cortex MCP server

## RefCertify — Codebase Index

Cortex's source at `C:\Claude Code\cortex` is indexed by RefCertify. Strict Saver posture: use RefCertify when it improves quality per token; raw `rg`/`Read`/Grep stays right for literal strings, exact paths, configs, logs, markdown, and generated text. Hook nudges are advisory, not gates. Every tool accepts `compact: true` for smaller payloads.

**Tool picks:** `refcertify_outline` (file shape) · `refcertify_find`/`refcertify_search` (symbols) · `refcertify_source` (one exact symbol) · `refcertify_slice` (symbol + direct helpers) · `refcertify_grep` (scoped raw text) · `refcertify_refs`/`refcertify_deps`/`refcertify_callers` (impact). `refcertify_help` is the compact router; `refcertify_route` is an evidence-grounded advisor, not a gate — treat its recommendation as a hint.

**High-leverage tools for refactor work in this repo:**
- `refcertify_callers(name)` — who calls a memory/retrieval function before you change its signature.
- `refcertify_diff_outline(refA, refB?)` — semantic diff of changed symbols across refs (great for reviewing migrations to `memory_items` or hotness).
- `refcertify_signatures([names])` — batch signature lookup when comparing query/* methods.
- `refcertify_unused_exports({path: 'src/'})` — dead-code finder; flag pre-`memory_items`-era exports.
- `refcertify_kind_index('interface', {path: 'src/db'})` — every type in a subtree.

`refcertify_pack` is last resort for broad context. It runs governor preflight and refuses only on strong evidence (telemetry gate fail, zero index evidence, true literal/config needle, extreme budget); use `preflight:true` to inspect, `force:true` only when broad context is intentional.

**Worktree rule:** RefCertify answers are root-bound. In a git worktree or any checkout other than the session's start root, confirm the active root via `refcertify_stats`/`refcertify_workspace` and bind it with `refcertify_workspace {action:"use", path:"<toplevel>"}` before trusting answers.
