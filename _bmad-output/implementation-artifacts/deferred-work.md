## Deferred from: code review of story-1.1 (2026-07-27)

Three review layers produced 24 findings; 17 were fixed in the story. These are the rest — each real, none able to produce a wrong contradiction verdict.

- **Contradiction detection is ASCII-only.** `TOKEN_PATTERN` (`src/memory/text.ts`) is `[a-z0-9][a-z0-9._/-]*`, so Cyrillic, CJK, fullwidth and accented content analyzes to an empty core and never conflicts. Fails safe — a silent miss, not a wrong answer — and is now stated as a known limit in `conflict.ts` and the README. A `\p{L}\p{N}` pattern with the `u` flag would close it, but `TOKEN_PATTERN` is shared with `query/retrieval.ts` and the rerank layer, so changing it moves `output_tokens` on the locked suites and needs its own story with a gate run.

- **`promoteSubagentNotes` re-activates an arbitrary prior.** `src/capture/consolidate.ts:288-310` picks the *first* same-kind+subject parent note via `Array.prototype.find` — including one superseded long before the child ran — and re-activates it unconditionally. That was deterministic when only one note per (kind, subject) could be active; the AD-17 veto ends that guarantee, so a promotion can now leave three active decisions on one subject. Story 1.1 narrowed the blast radius (the already-contested veto stops the extras being silently archived) but did not fix the re-activation itself. Not reachable from the live hook path — `promoteSubagentNotes` has no in-repo runtime caller, only `src/index.ts`'s export and `tests/consolidate.test.ts` — so it is reachable through the library surface only. Epic 5 owns subagent note promotion and should fix it there.

- **`cortex_resolve --subject` in the CLI has the same ambiguity the MCP tool now refuses.** `src/transports/cli.ts:497` still calls `findActiveNoteBySubject` directly. The MCP path refuses to guess while a contest is open; the CLI path does not. Same fix applies, but the CLI resolve command has no test coverage for contested subjects and adding it is a small story of its own.

- **`notes.conflict` carries no counterpart id.** Conflicts are cleared per *subject*, so resolving one side clears every contested note on that subject. With three-way contests this over-clears — a pair unrelated to the resolved one loses its marker. Correct for the two-note case, which is what detection produces today. A `note_conflicts(note_id, counterpart_id)` join table would make it exact and would also give SM-5 a per-pair resolution rate, but it is a new table and R1 has already spent its one `SCHEMA_VERSION` bump on Story 3.1.

## Deferred from: code review of story-0.2 (2026-07-24)

- **Concurrent spool appends tear lines above the stdio buffer.** `hooks/claude/cortex-capture.sh` appends with `printf '%s\n' "$LINE" >> "$SPOOL"`, which is atomic only up to roughly one stdio buffer. Measured by a reviewer with 16 concurrent hook invocations: 848-byte lines 16/16 intact, 2.8 KB 13/16, 53 KB 14/16 — torn lines are then silently dropped by `parseSpoolLines`. The `Bash` branch embeds uncapped `stdout`/`stderr`, so a real failing-test capture lands well past the safe size. Predates agent identity; parallel subagents make it easier to hit. Likely fix: cap the captured streams inside the existing jq program (e.g. `.[0:2000]`), which costs no extra process, and/or write via a per-PID temp file. Wants a measurement-backed story of its own.

- **B-4 (≤15 ms PostToolUse) is not achievable on the Windows/Git Bash target.** Measured ~400 ms per hook invocation on the dev machine; `bash -c 'exit 0'` alone is ~36 ms, so the budget is exceeded before the script runs a line. Pre-existing and not caused by any R1 story, but story 0.2's AC #1 binds it, so AC #1's third clause is **not met, with cause**. N-4 (no Node spawn per tool call) does hold. The budget needs re-basing against the real platform the way B-4a was already amended for the substitution path — a PRD decision, not a code fix. Carry to the Epic 0 retrospective.

- **Agent-id uniqueness across primaries is now a load-bearing host assumption.** `getSessionByAgentId` filters by neither parent nor status — deliberately, because story 0.2's AC #3 requires a child to stay findable after its parent ends. Consequence: if a host reuses an `agent_id` in one scope across two primaries, the second primary's subagent work is written into the first primary's (ended) child. Claude Code reports per-dispatch UUIDs so this does not arise today. Worth stating in the architecture spine rather than patching, since the alternative breaks AC #3.

- **The `status: resolved` sniff is still duplicated.** `src/query/render.ts` and `src/query/state.ts` each inline `item.text.toLowerCase().includes('status: resolved')`, one line from the now-centralized `isContested`. It carries the identical text-sniff flaw and the two copies can drift (they already differ in position relative to `renderReferenceLabel`). Centralize it when `notes.conflict` gets a real `memory_items` column — the release that can afford a `SCHEMA_VERSION` bump fixes both sniffs at once.

- **`recall` can exceed its token budget by the trimmed-hint line.** `assembleBudgeted` (`src/query/recall.ts:60-79`) refuses to drop the last evidence line so the budget can never silence the top result, then appends the hint regardless — 51 tokens against a requested 10. Pre-existing and not contested-specific; now pinned by a test in `tests/recall.test.ts` so it is at least visible. Deciding whether the hint should be droppable is a product call, not a bug fix.

- **The eval gate covers only the recall surface.** `QualityFixture` (`src/eval/harness.ts:20-31`) has no assertion hook for `header` or `full_state`, and `runEvalGate` compares neither, though the baseline records both. Deleting the contested marker from `renderNoteBullet` would leave `npm run gate` green — caught only by unit tests. Adding output assertions for those two surfaces would close it.

- **The contested fixture's adversarial property is itself ungated.** `eval/suites/contested.json` exercises the reorder only because the uncontested insight (47.10) sits between the two contested decisions (53.00 / 45.30). If ranking ever drifts so the pair becomes naturally adjacent, the `"[contested]\nDecision ["` needle passes without the reorder running and nothing goes red. The unit tests pre-assert the split explicitly; the fixture format has no equivalent hook.

- **`state`'s kind-section grouping has no adversarial integration test.** Section order is hotness-based and no configuration reachable through the public API split a same-kind contested pair there, so the grouping call is defensive. It is covered by unit tests on `groupContestedAdjacent` / `groupContestedWithinKind`; an integration test that passes regardless was removed rather than kept.

- **`RecallOptions.limit` is uncapped against an O(n²) grouping scan.** `recall` is public API and `limit` passes straight through; `groupContestedAdjacent` is quadratic in the result count. In-repo callers use n = 8 (`src/transports/mcp.ts` never sets it), so this is theoretical today, but `recall(store, topic, { limit: 5000 })` with all results contested would run ~12.5M synchronous iterations.
