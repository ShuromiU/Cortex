## Deferred from: story-2.5 create-story (2026-07-31)

- **Two source files contain raw NUL bytes, and every text search silently skips them.** `src/transports/hook-entry.ts` (offset 11476) and `src/query/reference-validation.ts` (offsets 7606, 8053) each hold a literal `0x00` inside a template literal used as a cache-key separator — `` `${a}\0${b}` `` written as an actual control byte rather than the escape. The strings are behaviourally correct, so nothing fails; the cost is entirely in tooling. ripgrep, grep, and `certify_refs`'s text pass all classify these files as binary and omit them **without saying so** — `rg -n "findDbPath" src/transports/` returns two files, `rg -na` returns three. Story 2.5 hit this directly: `hook-entry.ts` holds one of the four `findDbPath` derivations, and a text-only enumeration would have relocated the store while leaving the SessionStart transport pointing at the old path. `certify_refs` on `.cortex.db` returned 17 union sites and did not include it either.

  Provenance: `reference-validation.ts` from `4f95366`/`43bf0d9`, `hook-entry.ts` from Epic 0's `1982226` — the bash-heredoc escape-collapse failure mode, where `\0` in a heredoc becomes the byte it denotes. **Fix is three characters per site** (`\0` written as source text), changes no behaviour, and is worth doing standalone rather than inside a story that would then have to prove the source edit and the relocation are independent. Until then, enumerate with `rg -a` or via LSP in these two files, and treat "text search found nothing here" as unproven.

## Deferred from: story-2.5 implementation (2026-08-01)

- **A long-running MCP server keeps writing to the pre-relocation store.** It resolves its database path once at startup, so a server already running when the package is upgraded holds the old `<project>/.cortex.db` until it is restarted. Observed live: the original kept accruing sessions for hours after migration while the new store accrued its own. Nothing is lost — the original is retained by AC #3 anyway — but the two diverge, and whichever session restarts last "wins" the newer memory. A fix means either detecting the moved store from inside a running process or having `install`/`doctor` tell the user to restart. Belongs with whatever story next touches MCP lifecycle.

- ~~**Two worktrees that each carried their own pre-relocation `.cortex.db` migrate only one of them.**~~ **PARTLY CLOSED in the 2.5 review repair.** The original entry was wrong on its own mitigation: it claimed `doctor` would report the un-migrated file as "not migrated yet" forever, and `doctor` in fact reported **"migrated"** and told the user to delete it — the inverted safety net a reviewer caught. Two fixes landed: the search order now puts the **main** worktree first (a first command run inside a linked worktree was migrating that worktree's small store and permanently shadowing the main checkout's real one — measured at 60 notes replaced by 0), and `doctor` now reports migration from the recorded `migrated_from` rather than inferring it. What remains deferred is genuinely only the merge: when two worktrees *both* hold a pre-relocation store, the main one wins and the other is reported as present-and-not-migrated. Merging is a real data question (duplicate ids, conflicting notes, overlapping sessions) and needs a `cortex import <db>` with a documented conflict rule.

- **A sibling checkout that is transiently unavailable can be adopted away.** `findAdoptionCandidates` matches on the root-commit OID, which clones and forks share, and treats "recorded path does not exist" as proof the store is orphaned. An unmounted share, a folder mid-rename or a restore in progress satisfies that. Adoption is a move, so the live checkout loses its store and is not even offered it back. Mitigated for now by preview-by-default plus an explicit warning in both the `adopt` preview and `doctor`'s fix text; a real fix needs a liveness signal stronger than `existsSync` — a recorded machine/volume id, or a lock file the owning checkout refreshes.

- **`findAdoptionCandidates` opens every store under `$CORTEX_HOME/projects`.** Fine at today's scale (one file open and two `meta` reads each, only when the current project has no store at all), but it is O(projects) on a cold start for a moved repository. If a user accumulates hundreds of projects this wants an index — a small `projects.json` keyed by root-commit OID — rather than a directory scan.

- **Adoption clears only the first candidate.** `cortex adopt` acts on `candidates[0]`, sorted by size, and there is no way to choose another or to see more than the largest in `doctor`'s single line. Two repositories sharing a root commit (a fork of a fork) whose paths are both gone would present two, and the CLI offers no selection. Rare enough to defer; needs `cortex adopt --from <path>`.

## Deferred from: code review of story-2.2 (2026-07-28)

- **The IMMEDIATE-transaction guarantee has no automated test.** `updateMemoryItemText` and `deleteMemoryItemCascade` now use `runInImmediateTransaction`, matching `insertNote`/`updateNoteStatus` and the rule CLAUDE.md states. The failure it prevents — `SQLITE_BUSY_SNAPSHOT` bypassing the busy handler on a lazy lock upgrade — is only observable when a **second process** holds the write lock; a reviewer reproduced it that way. An in-process attempt passed under both DEFERRED and IMMEDIATE, so it was removed rather than kept as a test that proves nothing. Closing this needs a two-process harness (spawn a child that opens the same file and holds a write transaction), which is a small story of its own and would also cover `insertNote`'s identical guarantee, currently equally untested.
- **`cortex gc`'s command-run overflow prune is undone by the backfill.** `gc.ts` deletes overflow `command_run` rows from `memory_items` without touching `command_runs` or the `events` rows behind them, so the next `ensureCortexSchema` rebuilds every one — measured by a reviewer at 5 items → gc → 2 → next command → 5. The cap bounds nothing. Story 2.2 documented the resurrection mechanism and fixed it for the deletion path; gc has the same bug and was explicitly out of scope. It should reuse `deleteMemoryItemCascade`'s chain rather than deleting projections directly.
- **`edit-memory` never re-runs or clears contradiction detection.** Editing a contested decision so that it no longer contradicts its counterpart leaves both notes at `conflict = 1` and both projections carrying `Conflict: true`, so they render `[contested]` forever; editing a note *into* a contradiction flags nothing. The correction command therefore cannot correct a false contest — only `cortex_resolve` can, and only by resolving a note the user wants to keep active. Re-running detection on edit is the obvious fix and is a behavior change worth its own story, since it can newly mark items contested as a side effect of a typo fix.
- **`note-resolve --status` silently coerces anything that is not `superseded` to `resolved`.** A typo like `--status supersede` resolves instead, which now also clears the contest and skips the FR-4 demotion. Pre-existing line; the consequences grew with this story. Validate against the closed set.
- **`--subject` normalisation differs between the guard and the resolver.** `getActiveNotesBySubject` normalises with `.trim().toLowerCase()`; `findActiveNoteBySubject` passes the raw string with `COLLATE NOCASE`. `--subject " auth "` therefore reaches a guard that sees the notes and a resolver that does not, and `COLLATE NOCASE` is ASCII-only while `toLowerCase()` is Unicode-aware. Same family as the missing tiebreaker below.

## Deferred from: code review of story-2.4 (2026-07-31)

- **`install` repairs the wiring in the file it owns, not in the others.** It now reads all three settings files to avoid duplicating an event another one wires, but if that other file's entry is itself wrong — a stale matcher in `settings.local.json`, say — the run reports `unchanged` and the defect stands. Repairing across files means writing to a file the user did not name in `--scope`, which is a bigger decision than this story should take.

If a user genuinely has such a home directory, `--dir` is the only route and they must wire it themselves.
- **`renderInstallResult` and `runInstall` disagree about ordering guarantees.** Actions are applied in sequence and a refusal stops only its own action, so a refusal partway through leaves earlier writes in place. The summary now says so and lists them, but there is no rollback and no transaction. Making install atomic across four different file formats is a much larger design.
